# FleetIQ AI evals

Evals for the two AI features in `lib/ai/` — `generateSchedule` (maintenance
schedule generation) and `extractInvoice` (garage invoice photo extraction).
These live outside `tests/` on purpose: `npm run test` (vitest) only runs
free, pure logic. Everything in this directory that calls the real
Anthropic API costs money, so it's never run automatically.

Both scripts call `lib/ai/schedule.ts` / `lib/ai/invoice.ts` directly — no
HTTP server needed — because the Anthropic client is a parameter those
functions accept rather than fetching internally. That's also what lets
each script's `--selftest` mode swap in a fake client and prove the
scoring/assertion logic works without spending a cent.

## Invoice eval — `npm run eval:invoice`

A **gold-diff** eval: 15 synthetic Qatar garage invoice images
(`evals/invoice/images/inv-01.png` .. `inv-15.png`, generated by
`evals/invoice/generate-fixtures.ts` from HTML via Playwright) are each fed
through `extractInvoice`, and the result is scored against a hand-authored
gold answer (`evals/invoice/gold/inv-*.json`, matching `aiInvoiceSchema`).

The 15 fixtures deliberately include the hard cases a real photographed
invoice throws at a vision model: a handwritten-style odometer figure
(inv-05), a faded/low-contrast scan (inv-06), a ~3° rotated photo (inv-07),
an invoice with no odometer field at all (inv-08), a total printed in
Eastern Arabic-Indic numerals — ٢٥٠.٠٠ (inv-09), and a long multi-item
service history (inv-10) — alongside 10 more varied garages/services with
decimal QAR amounts.

Scoring normalizes both sides before comparing (`evals/lib/normalize.ts`,
unit-tested in `tests/eval-normalize.test.ts`):
- **Numbers** (odometer, total cost): parsed out of currency formatting or
  Eastern Arabic digits, compared with **zero tolerance**.
- **Dates**: normalized to ISO, comparing calendar day regardless of the
  original format.
- **Strings** (garage name): casefolded, punctuation-insensitive.
- **Line items**: scored as set overlap on normalized description
  (precision/recall/F1), not exact order or count.
- **null only ever matches null** — a confidently wrong number and a
  correctly-abstained blank are never treated as equal.

The script prints a per-field accuracy table across all 15 cases and
**exits 1** if `odometerKm`, `totalCostQar`, or `serviceDate` accuracy falls
below 80% — those three feed pre-filled numbers that matter (interval math,
cost-per-km, history ordering); a miss on `garageName` or a line-item
description doesn't corrupt any derived number the same way. Any image that
errors during extraction is logged explicitly and counted as a **failure on
every field**, not dropped from the denominator — a silently-dropped
unscorable case would otherwise inflate the reported accuracy.

```
npm run eval:invoice              # real run — needs ANTHROPIC_API_KEY, costs money
npm run eval:invoice -- --selftest # free dry run — no key needed, no network call
```

`--selftest` feeds each gold JSON back through `extractInvoice` via a fake
Anthropic client (so the exact same code path — including Zod validation —
runs, just without a real model call) and expects every gate field at
100%. It only proves the scorer accepts a CORRECT answer; run
`npx tsx evals/selftest.ts` (or `npm run test`, which wires it in) to prove
the same scorer also CATCHES a wrong one.

## Schedule eval — `npm run eval:schedule`

A **sanity/assertion** eval, not a gold-diff — there's no single "correct"
maintenance schedule for a 2022 Toyota Hiace to diff against (a legitimate
response could reasonably pick a 7,000km or 10,000km oil interval, Bosch or
Denso for the battery, different wording every run). Instead, `generateSchedule`
is called for 5 real vehicles and the result is checked against assertions
that hold regardless of exact wording:

- All 10 required categories present (oil change, oil filter, air filter,
  cabin filter, brake pads, tyres, battery, coolant, transmission fluid,
  belts) — matched by keyword against the item's normalized name, robust to
  the AI's exact phrasing varying run to run.
- Oil-change interval falls inside a real-world plausible range (5,000km –
  15,000km).
- Every item has at least one non-null interval, non-empty brand
  recommendations, and intervals inside the schema's own bounds.
- Battery is tracked by **time** (`intervalMonths`), not distance — a
  battery dies of age/heat, not km driven.
- Tyres are tracked by **distance** (`intervalKm`).

Vehicles covered: Toyota Hiace 2022 (2.8L diesel), Nissan Urvan NV350 2019,
Mitsubishi L200 2021 (diesel), Toyota Corolla 2023 (1.6L), Ford Transit 2020
(2.2L diesel).

```
npm run eval:schedule              # real run — needs ANTHROPIC_API_KEY, costs money
npm run eval:schedule -- --selftest # free dry run — no key needed, no network call
```

`--selftest` runs the same `checkSchedule` assertion function against a
hand-built valid schedule (expects 0 failures) and a deliberately broken one
— tyres removed, battery given a distance interval instead of a time one
(expects exactly those 2 failures to be caught).

## Cost estimate

Both scripts use Sonnet (`lib/ai/model.ts`'s `MODEL`). Rough per-run cost:

| Eval | Calls | Est. cost |
|---|---|---|
| `eval:schedule` | 5 vehicles | ~$0.02 per vehicle → ~$0.10/run |
| `eval:invoice` | 15 images | ~$0.03 per image → ~$0.45/run |

These are rough (actual token counts vary with response length); re-check
against current Anthropic pricing before budgeting a CI job around them.

## Keeping fixtures honest

`evals/invoice/generate-fixtures.ts` is the ONE place that defines both an
invoice image's content and its gold answer (see that file's header) — the
15 fixtures are synthetic stand-ins, not real garage receipts. As real
photographed invoices come in through the app, consider swapping some of
these synthetic images for real ones (with garage/customer details redacted
as needed) so the eval keeps tracking the actual failure modes real photos
produce, not just the ones this script anticipated. If a fixture image is
ever hand-edited after generation, its `gold/*.json` must be updated to
match by hand too — regenerating from `generate-fixtures.ts` again is
safer.
